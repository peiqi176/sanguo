## 2. 动新功能前必须先解决的 3 个结构问题

这三件不做，后面每加一个功能都要多还一笔债。

### 问题 1（🔴 会直接出 Bug）：`user://maps/` 被两套格式同时占用

```
user://maps/
├── 我的地图/          ← 地图工坊（MapEditor）写的
│     map.json + height.raw + height_preview.png + biome.png
└── 旧参数图/          ← MapSaveManager.save_current_map() 写的（legacy）
      params.json + biome.png
```

两边都用 `user://maps/`（`MapEditor.MAP_DIR` 与 `MapSaveManager.SAVE_DIR_LEGACY`），且
`MapSaveManager.list_maps()`（`:307`）只列目录名、不判格式，`get_map_params()` 找不到
`params.json` 就静默返回 `null`。后果：主菜单将来做选图界面时，会出现「点进去打不开」的幽灵条目。

**处理方案（M1-1）**：工坊统一写入 `map.json` 并用 `"kind": "mapforge"` 标记；`MapIO.list_maps()` 只认这个标记，legacy 目录归入「旧地图（只读）」分组；`MapSaveManager` 的三个 legacy 方法标注 `@deprecated` 但保留（随机地图流程还在用 `Terrain.params`，不依赖它们）。

### 问题 2（🟡 影响后续所有迭代速度）：`MapEditor.gd` 职责过载

532 行里塞了：环境构建、地形网格、网格叠加、笔刷圈、输入、拾取、笔刷算子、撤销、存档、UI 构建、Toast。
要再加对象层 + 调色板 + 检查器 + 生成向导，这个文件会突破 2000 行，改一处心惊一次。

**处理方案（M1-4）**：按职责拆成 5 个文件，`MapEditor.gd` 只留「生命周期 + 状态 + 输入路由」，压到 350 行以内。

### 问题 3（🔴 决定架构是否统一）：地图内容层还锁在 `Main.gd`

`_spawn_initial_forces / _spawn_decorations / _spawn_resource_nodes / _spawn_villages / _spawn_wild_horses`（5 个函数，约 280 行）是硬编码选址。

**处理方案（M2）**：不做「编辑器地图走一套、随机地图走另一套」，而是**两条路都先产出同一份 `objects[]`，再走同一个铺装器**。这条不做，往后每加一种对象都要改两处。

## 4. 核心接口契约（先定死，后面全部依赖）

> 三条硬规矩，违反就会返工：
> 1. **一律用 `preload()` 引用，不用 `class_name`。** 本项目在 headless / 新克隆仓库下踩过全局类缓存不存在的坑（`TerrainMaterial` 已经因此改回 preload）。
> 2. **地形图始终活在 `Terrain` 里，`MapDoc` 不持有 `Image`。** 编辑器直接改 `Terrain.heightmap_img`，保存时从 Terrain 导出。MapDoc 只存元数据和对象。
> 3. **坐标以 grid 为准**（`Vector2i`），世界坐标由 `grid_to_world()` 派生。地形改了建筑不会飘。

### 4.1 `MapDoc.gd`

```gdscript

# 网格与世界（world_size() == grid_n * cell_size，这条契约必须守住）

# 图尺寸
var heightmap_size: int = 256

# 地形参数字典（MapParams 全部 28 字段，保留"从这套参数再生成"的能力）

# 内容层

var regions: Array = []
var players: Array = []
var triggers: Array = []
var settings: Dictionary = {}

# --- 派生 ---
func world_size() -> float
func cell_count() -> Vector2i
func height_px() -> int                      # 高度图分辨率

# --- 序列化 ---
func to_dict() -> Dictionary
```

```jsonc

{ "kind": "unit",     "id": "sword",      "owner": "wei", "grid": [130, 22], "rot": 180 }
```

> `deco` 用世界坐标 `pos`（装饰允许非格对齐、允许叠放），其余全部用 `grid`。

### 4.5 `MapValidator.gd`

```gdscript
extends RefCounted

const ERR: int = 2
const WARN: int = 1
const INFO: int = 0

```

七项检查（对应方案 7.5）：

| code | 级别 | 判定 |
|---|---|---|
| `start_on_land` | ERR | 每个 player.start 所在格 `is_placeable` 且 15×15 可建面积 ≥ 60% |
| `start_distance` | ERR | 任意两起点切比雪夫距离 ≥ `grid_n * 0.25` |
| `resource_reachable` | ERR | 每方最近 wood/stone 用 A* 可达（限 3000 节点） |
| `object_overlap` | ERR | 建筑 footprint 互不重叠、不越界、不落水 |
| `land_connectivity` | WARN | 陆地四连通分量 > 1（水战图可在 settings 豁免） |
| `dead_resource` | WARN | 资源点周围 3 格全不可走 |
| `symmetry_deviation` | WARN | 声明了对称方式时，高度图镜像偏差 > 阈值 |

**为什么没收成"完全统一"（这条决策要记住）**

计划原方案是：程序生成也先产出 `objects[]`，再走同一个铺装器。但我实际改成了**分流**：

```
custom 且 doc 里有建筑  →  _spawn_from_doc(doc)
否则                    →  _spawn_decorations / _spawn_initial_forces / ...
```

理由是：把 `_spawn_initial_forces` 那 280 行（含"官府→牌楼→农夫→士兵→文臣"的相对偏移
和 `_find_placeable` 螺旋搜索）改写成"纯函数产数组"，必须**逐行模拟原顺序**，
任何一次 `is_placeable` 判断差异都会让所有开局位置整体偏移 —— 而这是玩家最敏感的手感，
现有代码已经调过很多轮。

**结论**：这个统一动作应当和 M4 的生成器一起做（生成器本来就要产出 `objects[]`），
那时有模板和校验器兜底，改坏了能立刻看出来。现在硬做，等于用最脆的手感去换一个还没人用的抽象。

**分流方案的判据是「有没有建筑」**，不是「有没有 doc」：
只画了地形没放基地的图，仍然回退程序生成 —— 否则玩家进图会发现自己连官府都没有。
这条在 `Main._ready()` 里有注释说明，改动前先读。

**M3-3 改法说明（和计划里写的不一样，这里解释为什么）**

计划里写的是"跑个 Python 脚本把 `offset_y` 统一为 0，`scale` 重算"。
真正动手时先量了一遍数据，发现按计划做会得到一张**全部陷进地里**的图：

| 贴图 | 内容底边留白 | 旧 `offset_y` |
|---|---|---|
| `wall_inner`（内城墙） | 0.0% | 0.6 |
| `barracks_sword` | 1.6% | 1.0 |
| `government`（官府） | 14.0% | 1.5 |
| `farm`（农田） | 21.3% | 0.6 |
| `stable`（马厩） | 20.3% | 1.0 |

**留白跨度 0%~21%，而手填值在 0.6~1.5 之间乱跑，两者零相关。**
把 `offset_y` 一律改成 0，等于让所有图按"画布底边"贴地 —— 留白 21% 的农田会浮起，
留白 0% 的城墙会正确，但 `scale` 重算也救不回这层关系，因为留白是每张图各自的属性。

所以改成**量出来**：

```
世界高度 world_h = 画布高 × pixel_size × scale
anchor_y = world_h / 2 − 底边留白(像素) × pixel_size × scale
```

`pixel_size` 由 `get_sprite_pixel_size()` 保证"世界高度只跟 ref_h × scale 有关，
与贴图像素分辨率无关"，于是整条链路与图片多大完全解耦。
`offset_y` 语义降级为「在地面之上额外抬升几米」的人手微调，默认 0。

**实测修正量**：官府 `1.8 → 2.70`、剑兵 `0.9 → 1.78`。
换句话说，改之前**每个兵都有约 1/4 的身子埋在地里**，而且埋的深度各不相同。

**M3 抓到的真问题**

- **★ `Sprite3D.transparency = BaseMaterial3D.TRANSPARENCY_ALPHA` 让所有精灵隐身。**
  Godot 4 里 `GeometryInstance3D.transparency` 是 **float 淡出值**（0 = 不透明，1 = 全透明），
  而 `BaseMaterial3D.TRANSPARENCY_ALPHA` 这个枚举恰好 **== 1.0**。
  于是"设成透明混合"实际执行的是"设成 100% 透明" ——
  贴图加载日志全部 `✅`，画面上什么都没有，`is_visible_in_tree()` 还是 `true`，
  单看代码和日志完全查不出来。这是从 Godot 3 抄过来的写法（Godot 3 里叫 `transparent` 布尔值）。
  全项目共 **13 处**，分布在 Unit / Building / ResourceNode / Village / WildHorse / SupplyCart /
  TransportTeam / Tree / Main 的 ghost，已全部删除（`StandardMaterial3D.transparency` 上的同名赋值是对的，保留）。
  删掉后单位、建筑、血条、僧侣、村庄、野马、辎重车、建造虚影**一次性全部显形** ——
  这也是这一版观感变化最大的一处。
  `_selftest_sprites` 里加了回归守卫，任何人再写回去会立刻红灯。
- **`ResourceLoader.exists()` 对刚导入的 PNG 返回 false**。原代码用它判断
  「根目录有没有」，false 之后会掉到 `assets/sprites/<category>/` 去找，
  必然找不到 → 表现成"导入成功但调色板还是方块"。
  正解是同时看 `FileAccess.file_exists()`：文件在、但没 `.import` 时用
  `Image.load_from_file()` + `ImageTexture` 兜底解码。
  这一条不修，M3-1 的"三步内可摆"就是假的（必须重启 Godot 等它重新扫描）。
- **`Image.get_used_rect()` 可以替掉原来那段"隔 2 像素抽样数不透明占比"的坏图检测**。
  它是 C++ 实现，快两个数量级；而抽样会漏掉细长内容（旗杆、栏杆）。
  顺带把"内容包围盒"这件事一次算好，贴地公式直接复用。

### M3.5 · 统一锚点重做 + 地面/移动/视角三处硬伤修复

这一节不是新增功能，是把"看着像能跑、其实一直不对"的东西修干净。
起因是用户一句话：**"没有铺地面，点击人物去某个地方会上下走动，自动寻路也有问题"**。

#### ① 地面根本没画出来（三个独立 bug 叠在一起）

| # | 问题 | 真相 | 修法 |
|---|---|---|---|
| 1 | 地形 MeshInstance3D 完全不可见 | **Godot 4 的 `PlaneMesh` 本来就是水平的 XZ 平面**（AABB 高 = 0），代码又 `rotation.x = -90°`，把地面立成了一堵墙 | 去掉旋转；改 `custom_aabb` 撑开，避免顶点位移后又被视锥剔除 |
| 2 | 高度场是白噪声 | `_noise.frequency` 被固定成 1.0，调用却写成 `get_noise_2d(wx * _noise.frequency)` = 用世界坐标原样采样。而 **`FastNoiseLite.frequency` 是内部生效的**（实测 prop=0.01@(37,11) 与 prop=1.0@(0.37,0.11) 结果完全相同）→ 每米变化 0.57，相邻像素高差 ±9 米 | 用 `MapParams.noise_frequency`（0.018），振幅 `height_scale` 0.90 → 0.35 |
| 3 | 地面惨白像纯色块 | ① shader 自己算光照塞进 `ALBEDO`，却**没写 `unshaded`**，引擎又照亮一次 → 过曝；② 贴图 uniform 缺 `: source_color`，sRGB 被当线性值 → 整体提亮一档；③ `tiling = 0.20` 等于把一张贴图拉伸 50 倍；④ 7 张地形贴图 `mipmaps/generate=false` | 光照交给引擎（vertex 写 `NORMAL`）；7 个贴图 uniform 加 `: source_color`；改成 `tile_size = 7m`；重导入开 mipmap |

顺带：水面同样是 `rotation.x = -90°` 立着的，一并修；水的波纹位移也从 `VERTEX.z` 改成 `VERTEX.y`。

**教训**：这三条里没有一条会报错。日志全是 ✅、`is_visible_in_tree()` 也是 true —— **只有实拍截图才能发现**。

#### ② 移动与寻路

| 问题 | 修法 |
|---|---|
| 点地面走到别处 | `SelectionManager._screen_to_world` 打的是 **Y=0 平面**，点在 6 米高的坡上会偏出去十几米。改用 `TerrainPicker` 打**地形表面** |
| 走起来上下抽 | 贴地每物理帧硬赋值，格子中心 2 米一采样 → 一格一跳。改为 `_snap_to_ground()` 平滑跟随（差 > 0.8m 直接对齐，否则 lerp） |
| 路径是楼梯 | A* 只有 4 方向。改 8 方向 + 斜向 √2 代价 + **防切角**（两个正交邻格必须都通） |

| 弹堆 O(n) | `heap_f.insert(0, x)` 每次搬整个数组 → 改成 `heap_f[0] = x` |

`CameraController` 默认改为 **俯角 45° / 偏航 45° / FOV 32° / 距离 18~110 m**。

| M4-6 | `MapValidator.gd`：7 项校验 | 新建 | M | 故意造错图，7 项都能报出来 |
| M4-7 | 校验结果面板：点击定位跳转 | `EditorUI.gd` | S | 双击错误条目，相机飞到该格 |
| M4-8 | 生成后进编辑器可手改（生成 ≠ 覆盖） | 流程串联 | S | 生成 → 改 → 存，改动能保住 |

**M4 最关键的一条：对称化不是锦上添花，是生成图能不能当正式图用的分水岭。**
不做对称，永远有一方吃亏，图只能当草稿。所以 **M4-2 必须排在其他生成任务之前**，其余模块都基于"已在对称约束下的高度图"来选址和铺设。

对称实现方式（写进代码注释，避免后来者改错）：
```
对高度图按对称群做「取最大值合成」：
  h'(p) = max over g in G of h(g·p)
这样任何地形特征都会在对方半场出现一份镜像，
起点到资源的相对关系天然对等。
```
